Ambiente: un venv condiviso, requisiti per ruolo

Un solo .venv alla radice del repo

  • base.txt (sempre): fastapi, uvicorn[standard], httpx, pydantic, pydantic-settings, python-dotenv
  • be.txt: langchain, langgraph, langgraph-checkpoint-sqlite, langchain-ollama, sqlalchemy
  • chat.txt: streamlit, requests, spacy, phonenumbers
  • voice.txt: websockets, numpy, faster-whisper, piper-tts, onnxruntime, sounddevice, phonenumbers, webrtcvad-wheels (opzionale)
  • dev.txt: pytest, pytest-asyncio, mypy

Come resta coerente

  • Ogni macchina installa base + il suo ruolo (venv leggero)
  • .venv/.setup_state.json salva lo sha256 di ogni file requirements
  • Se un collega cambia un file, al prossimo avvio is_setup() vede l'hash diverso e riparte da solo
  • --role all = tutto, per sviluppo e test
  • Pacchetti che richiedono compilatore C++ sono opzionali: se falliscono si va avanti con un avviso

Python ≥ 3.10 (consigliato 3.11/3.12; qui 3.13.5). Il setup usa solo la libreria standard: funziona anche con un venv rotto.

L'entrypoint nel dettaglio: funzione per funzione

#FunzioneCosa faSe qualcosa va storto
1git_pull()git pull --ff-onlysi ferma e stampa l'errore: non forzare
2resolve_role() · ensure_identity()ruolo da --role / LAN_ROLE / macchina.json / domanda; IP rilevatolo chiede una sola volta
3ensure_environment(role)confronta gli hash e installa solo se servesi ferma: rilanciare dopo aver sistemato
4configure_env()scrive BACKEND_BASE_URL, BE_URL, HOST nel .enverrore solo se manca .env.example
5firewall_hint()netsh advfirewall per ogni porta del ruolonon blocca: stampa il comando da admin
6wait_for_be()GET /api/health ogni 2 s, max 180 s (solo CHAT e VOICE)«BE assente»: il componente non parte
7start_component()processo principale + servizi extra, log liveCtrl+C ferma tutto

Codice: entrypoint/avvia.py (main) e lan/machine_setup.py. --status e --attendi usano gli IP di lan_config.json: con IP statici si fissano con --pubblica-ip.

LAN: ruoli, porte e cancello sul BE

RuoloCartellaPortaHealthServizi aggiuntivi
BEbackend/8000/api/health+ sito vetrina :8080 (http.server su frontend/)
CHATchat/8501 (Streamlit)/_stcore/health+ API del sito :8002 (uvicorn chat/api.py)
VOICEvoice/8003/healthWebSocket /ws/voice · sito / · test /test-voice

Regole di avvio

  • Ordine: BE → CHAT → VOICE (ordine_avvio in lan_config.json)
  • CHAT e VOICE non partono finché il BE non risponde (gate di 180 s)
  • Tutto è dichiarato in lan/lan_config.json: comando, cwd, porte, health, variabili

Perché così

  • Gli IP in lan_config.json sono esempi: quelli veri si chiedono una volta e si ricordano in macchina.json (non in git)
  • Così il giorno della demo il presentatore tocca un solo PC: avvia.py --attendi

Come proviamo senza il resto del sistema

  • Stub BE (voicebot/devtools/stub_be.py): un BE finto con registrazione, conferma sì/no, modifica, cancellazione
  • Test ermetici: conftest isola dal .env e spiega l'interprete sbagliato
  • voice local: stub + server + browser con un comando

Come capiamo cosa non va

  • python -m voicebot doctor: python, .env, pacchetti, modelli, audio, porta, BE, registrazione
  • /diag e tab STATO della pagina di test mostrano lo stesso report
  • Log JSON a una riga: facili da filtrare
