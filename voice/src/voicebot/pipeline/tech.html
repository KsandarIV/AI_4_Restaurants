2 · Models and dependencies

Models (local)

LLM gemma4:12b via Ollama (BE machine) · STT faster-whisper tiny · TTS Piper it_IT-riccardo-x_low (voice/models/) · VAD: energy by default.

Dependencies

Per-role files in setup/requirements/ (base + voice): fastapi, uvicorn, httpx, pydantic, numpy, phonenumbers, faster-whisper, piper-tts, onnxruntime, sounddevice (optional: spaCy NER).

3 · Key decisions

TopicChoice
BehaviourIdentical to the chat bot: same registration dialogue, same anonymiser, same BE endpoints. No local intent shortcuts: the BE agent decides everything.
LatencyLLM tokens feed the TTS as they arrive; synthesis per sentence; models loaded once at startup and shared by every call.
InterruptionBarge-in: speech longer than BARGE_IN_MIN_MS cancels the running turn, drops queued audio and tells the client; clicks and echo are ignored.
ResilienceTimeouts everywhere, retry/backoff (never replaying a non-idempotent POST), bounded queues, client reconnection with backoff, graceful shutdown.
PrivacyName and phone go only to POST /api/customers; the LLM sees an anonymous customer_id and [TYPE_N] placeholders; logs never contain what the caller said.
BE contract/api/health, POST /api/customers, POST /api/chat, POST /api/chat/stream (SSE).

4 · Strengths / weaknesses

Strengths

Natural, interruptible voice · on-premise (no API costs, data stays in-house) · resilient · diagnosable (python -m voicebot.doctor, /diag) · testable without network or models.

Weaknesses and mitigations

Slow first token (the BE runs the whole inference first; v2 hides it with a single spoken reply) · STT tiny on CPU (upgrade with a GPU) · no authentication on WS/BE (LAN demo only; add tokens in production).
